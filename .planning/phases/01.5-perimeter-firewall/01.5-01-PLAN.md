<objective>
Preparar la red de Host 6 para recibir la VM OPNsense: crear el bridge interno vmbr_wan (172.16.0.0/30) que actúa como WAN virtual para OPNsense, activar MASQUERADE de kernel (wlan0 NAT) para que OPNsense tenga salida a internet, y crear vmbr_lan sobre eth0 con IP 10.0.0.254/24 que será la interfaz LAN de OPNsense hacia el resto del lab.

Purpose: wlan0 de Linux no puede ponerse en modo bridge directamente con una VM — la única vía es que el kernel del host haga NAT (MASQUERADE) y OPNsense vea un enlace WAN virtual (vmbr_wan). Sin este preparativo en Host 6, la VM OPNsense no puede desplegarse en el Wave 2.

Output: Dos scripts bash: host6-firewall-setup.sh (wlan0 + vmbr_wan + iptables) y configure-vmbr-lan.sh (vmbr_lan sobre eth0). El operador los ejecuta en Host 6 con SSH root.
</objective>

    Lo que hace el script al ejecutar con --apply:

    1. VERIFICAR que wlan0 existe y tiene IP asignada (ip addr show wlan0 | grep 'inet '). Si no tiene IP, imprimir "ERROR: wlan0 no tiene IP — asociar al WiFi antes de continuar" y salir con exit 1. Esto bloquea al operador antes de un estado inconsistente.

    2. HABILITAR ip_forward del kernel de forma permanente: escribir `net.ipv4.ip_forward=1` en /etc/sysctl.d/99-ipforward.conf y ejecutar `sysctl -p /etc/sysctl.d/99-ipforward.conf`. No usar /etc/sysctl.conf directamente.

    3. CREAR vmbr_wan en /etc/network/interfaces como bridge interno sin bridge-ports (ningún NIC físico — es un bridge virtual puro):
       ```
       # vmbr_wan — WAN virtual bridge para OPNsense (Host 6)
       # Host 6 kernel hace NAT: vmbr_wan → wlan0 → Internet
       auto vmbr_wan
       iface vmbr_wan inet static
               address 172.16.0.1/30
               bridge-ports none
               bridge-stp off
               bridge-fd 0
               post-up   iptables -t nat -A POSTROUTING -s 172.16.0.0/30 -o wlan0 -j MASQUERADE
               post-up   iptables -A FORWARD -i vmbr_wan -o wlan0 -j ACCEPT
               post-up   iptables -A FORWARD -i wlan0 -o vmbr_wan -m state --state RELATED,ESTABLISHED -j ACCEPT
               pre-down  iptables -t nat -D POSTROUTING -s 172.16.0.0/30 -o wlan0 -j MASQUERADE
               pre-down  iptables -D FORWARD -i vmbr_wan -o wlan0 -j ACCEPT
               pre-down  iptables -D FORWARD -i wlan0 -o vmbr_wan -m state --state RELATED,ESTABLISHED -j ACCEPT
       ```
       Usar post-up/pre-down en /etc/network/interfaces para que las reglas iptables sean persistentes sin requerir iptables-persistent. Este es el patrón Proxmox estándar.

    4. AÑADIR el bloque vmbr_wan al final de /etc/network/interfaces del host (hacer backup primero, igual que network-setup.sh). Si el archivo ya contiene 'vmbr_wan', imprimir "SKIP: vmbr_wan ya existe en /etc/network/interfaces" y no duplicar.

    Lo que hace el script:

    1. VERIFICAR que eth0 existe: `ip link show eth0` (o el NIC pasado como parámetro $1, default eth0). Si no existe, exit 1 con mensaje claro.

    2. VERIFICAR que vmbr0 existe en /etc/network/interfaces. Si existe y tiene bridge-ports eth0, advertir que vmbr_lan duplicaría el bridge sobre el mismo NIC. En un lab con vmbr0 ya configurado en Host 6 sobre eth0, OPNsense LAN debe conectarse a vmbr_lan (bridge separado con la IP gateway) en lugar de vmbr0. El script documenta esto en su cabecera.

       NOTA ARQUITECTURAL importante (incluir en comentario del script): En Host 6, vmbr0 puede tener bridge-ports eth0 desde Phase 1. vmbr_lan es un bridge SEPARADO también sobre eth0 — esto es válido en Linux (un NIC puede pertenecer a múltiples bridges en la misma subred solo si tienen IPs distintas, pero crea ambigüedad de routing). La solución correcta es: si vmbr0 ya existe con bridge-ports eth0 en Host 6, reasignar la IP 10.0.0.254/24 a vmbr0 en lugar de crear vmbr_lan. El operador debe decidir en el checkpoint Wave 1. El script ofrece ambas opciones: --mode=new-bridge (crea vmbr_lan) o --mode=reuse-vmbr0 (añade IP 10.0.0.254 a vmbr0 existente).

    3. En modo --mode=new-bridge (default): añadir al final de /etc/network/interfaces:
       ```
       # vmbr_lan — LAN bridge de OPNsense (Host 6)
       # OPNsense vtnet1 se conecta aquí; eth0 lleva el tráfico al switch y al resto de hosts
       # IP 10.0.0.254/24 = default gateway de toda la red MGMT
       auto vmbr_lan
       iface vmbr_lan inet static
               address 10.0.0.254/24
               bridge-ports eth0
               bridge-stp off
               bridge-fd 0
       ```

    4. En modo --mode=reuse-vmbr0: mostrar instrucción para que el operador cambie la IP de vmbr0 en /etc/network/interfaces a 10.0.0.254/24 manualmente, sin aplicar cambios automáticos (demasiado riesgo de cortar SSH).

    5. APLICAR en modo new-bridge con `ifup vmbr_lan` solamente si se pasa --apply.

    6. VERIFICAR: `ip addr show vmbr_lan | grep '10.0.0.254'` y `bridge show vmbr_lan`. Imprimir PASS/FAIL.

    Parámetros: `configure-vmbr-lan.sh [eth0] [--mode=new-bridge|reuse-vmbr0] [--apply]`

## Trust Boundaries

| Boundary | Descripción |
|----------|-------------|
| wlan0 (WiFi público/semi-público) → vmbr_wan → OPNsense | Tráfico no solicitado desde internet no debe entrar al lab. OPNsense WAN firewall (stateful, bloquear entrante) es la primera línea. |
| vmbr_wan (172.16.0.0/30) → kernel Host 6 | Double-NAT aceptable en lab. El kernel Host 6 solo hace MASQUERADE de salida — no acepta conexiones entrantes hacia el lab sin que OPNsense las reenvíe explícitamente. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1.5-01 | Spoofing / Elevation | iptables MASQUERADE en kernel Host 6 | mitigate | Reglas FORWARD solo permiten tráfico iniciado desde vmbr_wan hacia wlan0; tráfico entrante desde wlan0 → vmbr_wan solo si RELATED,ESTABLISHED. Reglas codificadas en post-up de /etc/network/interfaces — persistentes y auditables. |
| T-1.5-02 | Information Disclosure | wlan0 expuesto a red WiFi compartida | accept | Lab de investigación en entorno controlado. OPNsense WAN bloquea entrante. Riesgo aceptado: no hay datos sensibles en tránsito durante esta fase de setup. |

| T-1.5-SC | Tampering | Instalaciones de paquetes npm/pip/cargo | n/a | Este plan no instala paquetes externos. Solo bash y herramientas del sistema (iptables, ip, bridge). |
